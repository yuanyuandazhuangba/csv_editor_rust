一、项目概览

原 Python/PyQt6 工具（1.3_nodask.py，4227 行）的 Rust 重构，专注超大 CSV 文件的读取、预览、筛选、拆分、列操作、哈希与导出。实测可处理 6.5GB / 901 万行 / 55 列 的数据，打开约 4 秒、峰值内存约 148MB，最终产物为兼容 Windows 7 的单文件 exe（约 7.4MB，无外部 DLL 依赖）。

二、分层架构

核心原则：数据引擎（core）与 GUI 层严格分离，core 无任何 GUI 依赖，可独立编译、单元测试与命令行调用。

三、核心引擎设计

3.1 读取器（reader.rs + csv.rs）

  • mmap 内存映射文件（不载入内容，仅映射虚拟地址空间）。
  • 流式行索引：分块顺序读文件构建行偏移索引（build_index_streaming），不触碰 mmap 页，避免把 6.5GB 文件整体拉入工作集 —— 这是内存降低两个数量级的关键。
  • 引号感知：CSV 状态机（csv.rs）处理双引号包裹字段、字段内换行、"" 转义、CRLF / CR / LF 换行。
  • 惰性字段访问：按 (行, 列) 取原始字节，仅在需要时解码为 UTF-8。行偏移索引内存约 8B/行，O(行数)。
  • UTF-16 文件在字节级无法安全切分（分隔符含 0x00），打开时整体转码为 UTF-8 再走统一路径。

3.2 编码检测（encoding.rs）

修正 Python 版“chardet + GB18030 优先”会把 UTF-8 文件误判为 GB18030 产生乱码的问题。改为严格验证优先：

BOM → 严格 UTF-8 验证 → UTF-16 启发式 → GB18030 兜底
UTF-8 是自校验编码，严格验证可靠；GBK/GB2312 等必然通过不了 UTF-8 验证而正确落到 GB18030 超集。所有数据内部统一为 UTF-8 String。

3.3 数据模型（model.rs）— 全文本模式

  • 所有列一律视为文本（TypeKind::Text），避免数值类型影响导出，保证长数字 / 前导零 / 大整数不丢精度。
  • classify 保留用于诊断/测试（整数 ≤18 位、浮点、>18 位长数字 → 文本、特殊浮点文本），不再参与导出类型判断。
  • row_into 复用目标容量，避免大数据逐行遍历时的字符串分配。默认采样 DEFAULT_SAMPLE_ROWS = 1000。

3.4 筛选引擎（filter.rs）

  • 10 种条件：等于/包含/不包含/大于/小于/大于等于/小于等于/不等于/空值/非空值；条件间用且/或组合，AND 短路。
  • 数值比较优先：整数用 i128 精确比较（覆盖 19 位卡号），浮点回退 f64；双方均可数值化时数值比较，否则字符串比较（trim 后）。
  • 并行分块评估（std::thread::scope），进度回调；并行度上限 MAX_FILTER_THREADS = 32。实测 200 万行 × 15 列（326MB）：单条件 0.046~0.057 秒。
  • 整行只解析一次（RowReader）：线程局部的行读取器把本行所需列的文本写进复用 String，同一行的多个条件共享这一次解析。此前每个条件各调一次 model.field(row, col)，每次都重新解析整行并分配 Vec<Vec<u8>>、每字段一个 Vec<u8> 与一个 String——条件越多重复解析越多，而且即使只取一列也要解析全部列。
  • 底层解析用零分配的 csv::parse_record_into（复用内容缓冲 + 字段偏移表），与 parse_record 语义一致，并有逐字段一致性测试守护（覆盖引号、"" 转义、空字段、字段内换行、中文字段等边界）。
  • 实测（优化前 → 优化后，同机同期、重复 3 次取最小）：1 条件 0.258s → 0.051s（并行度 12.8 → 27.0）；5 条件混合 0.297s → 0.057s；CPU 时间 3.3s → 1.4s。
  • 结果行号用 u32（支持 ≥43 亿行）。

3.5 拆分引擎（split.rs）

  • 按字段拆分单遍哈希分组 O(N)，消除 Python 版 df[df[col]==value] 的 O(N×U) 重复全表扫描。
  • 文件数上限保护 MAX_SPLIT_FILES = 20000；重名文件自动追加序号（Python 版直接覆盖）。
  • 文件名清洗：替换 Windows 非法字符与控制字符、压缩连续下划线、按字符边界截断 100 字符。
  • 多列组合键用 \x1F 连接，避免歧义。
  • 按行数拆分：并行写出。各批的行区间与输出文件彼此独立，按批号用原子计数分派给工作线程；并发度取核数但不超过 8（拆分是 IO 密集型，同时打开过多输出文件在机械盘/网络盘上会因寻道竞争变慢）。实测 200 万行 × 15 列（326MB）：4.61s → 0.66s，并行度 1.00 → 7.15。
  • 按字段拆分 XLSX：第二阶段并行转换。两阶段拆分中「中间 CSV → XLSX」的各分组相互独立，可安全并行；并发度上限取 6，因为每个转换会把该分组的全部单元格驻留内存，同时进行过多会显著抬高进程峰值内存。实测 47.66s → 18.27s，并行度 0.97 → 3.72。
  • 按字段拆分（CSV）仍为单线程，这是刻意取舍：它要求“每个分组内的行序与源文件一致”，并行写同一文件会打乱顺序；可行的并行化要么两遍扫描（先算 key 再随机读回），要么按块切分临时文件再合并（临时文件数 = 块数 × 分组数），代价与收益不成比例。该路径只做单线程内的开销优化：分组 key 写入复用缓冲，命中已有分组时用 &str 借用查询（HashMap<String, _> 实现 Borrow<str>），只有首次出现新分组才 clone 一份 owned key（实测 5.62s → 5.28s）。
  • CSV 写出路径：CsvWriter::write_row 需要引号时按引号位置分片写出（早期实现是逐字节 write_all）。两条实测教训：不要在中间 Vec 里拼整行再写出（多一次整行拷贝，按字段拆分反而慢 14%）；needs_quote 保持用 str::contains（底层 memchr），改成手写逐字节扫描会慢约 7%。
  • 拆分完整性核对：每次拆分后，各输出文件会被读回重新统计数据行数（count_data_rows：流式、引号感知、不建索引，对超大文件也只是一次顺序读），与写入时累计的行数逐文件对照，并统计「全部输出合计」是否等于「数据来源行数」；结论写入操作日志（逐文件行数 + 合计 + 核对通过/未通过）。XLSX 两阶段模式下核对的是「转换时读回的中间 CSV 行数」，XLSX 自身的行数由写出 API 逐行写入保证。相关测试：count_data_rows_is_quote_aware、split_report_reconciles_row_counts。
  • 拆分完整性核对表：拆分完成后在输出目录自动写出 拆分完整性核对表.csv（utf-8-sig，Excel 可直接打开），内容包括拆分类型、拆分依据、输出格式、数据来源行数、输出文件数、输出总行数、完整性核对结果，以及逐文件的「数据行数 / 写入行数」明细与合计行 —— 便于随数据一起归档与复核。相关测试：checkfile_contains_all_required_items。
  • 性能基准：src/bin/split_bench.rs（cargo run --release --bin split_bench -- [行数] [重复次数]），输出各场景墙钟耗时、进程 CPU 时间与平均并行度（CPU/墙钟，≈1.0 即单核）。单次测量有 ±10% 抖动，故默认重复 3 次取最小值。

3.6 列操作 / undo-redo（column_ops.rs）

Python 版每次操作 df.copy(deep=True) 深拷贝整表 + 20 步历史，6.5GB 数据单次拷贝即 OOM。
  • 本引擎以操作描述（派生列 DerivedColumn）记录，零复制零物化；字段在访问时按需计算。
  • 删除/隐藏为视图层操作（不物理重写 900 万行数据）。
  • undo/redo 为命令式栈：undo 弹出并反向执行，redo 重放，同样零复制。
  • 派生列类型：SplitField / Merge / Copy / Constant / Hash。

3.7 导出引擎（export.rs）

  • CSV：utf-8-sig（带 BOM） 流式写出，与 Python 版一致。
  • XLSX：超过 XLSX_MAX_ROWS_PER_SHEET = 1_048_576 自动分 sheet（Python 版直接崩溃）；超过 Excel 上限 16384 列则报错改用 CSV。
  • 全文本导出：所有列一律按文本（@ 格式）写入，长数字 / 前导零 / 大整数不会被 Excel 数值化，从根本上杜绝科学计数法与精度丢失（不再依赖“列名关键词 + 数据采样”的启发式长数字列识别）。
  • 公式注入防护（CWE-1236）：以 = + - @ 开头的字段加 ' 前缀；内部中转文件用 new_raw 关闭。

3.8 多文件合并（merge.rs）

  • 表头校验前置：read_file_header 只读文件开头（最长 64KB），按检测到的编码解码后取第一行解析，不构建行索引；否则 CsvFile::open 对 6.5GB 文件每个要约 4 秒，选十几个文件校验就要一分钟。
  • 一致性判定：check_headers 分三档——完全一致 / 字段相同仅顺序不同 / 存在字段名差异；差异字段名由 exclusive_fields 列出，供界面提示。
  • 按字段名对齐：合并时建立「目标列 → 源文件列」映射（按名称 position 查找）而非按位置拼接，因此各文件列顺序不同也能正确合并，源文件缺列写空值。
  • 共有字段交集：表头不一致时按用户选择取 common_fields（首个文件顺序去重后的交集）。
  • 流式写出：输出 utf-8-sig CSV，用 CsvWriter::new_raw（不加公式注入的 ' 前缀）——合并结果是数据而非 Excel 导出目标，加前缀会污染负数、加号开头的字段。
  • 合并结果写入临时文件后按普通单文件打开，从而复用筛选 / 拆分 / 列操作 / 导出的全部能力；再次合并前会清理上一个临时文件。

3.9 去重引擎（dedup.rs）

  • 语义：在传入的行集合（界面传当前筛选结果，未筛选时为全部数据）内，按 key 列的值组合判断重复，保留每条重复记录中首次出现的行，因此结果行序与输入一致。
  • key 拼接用  分隔：避免 ("ab","c") 与 ("a","bc") 被判为同一行（有专门测试守护）。
  • 零分配逐行处理：复用筛选同款 RowReader（整行只解析一次、字段文本零分配），key 也用同一个复用 String 构建；命中已有 key 时以 &str 查询去重表，只有新唯一行才 clone 一份 key。
  • 越界列容错：丢弃超出当前列数的字段索引（界面可能传入陈旧索引），全部越界时退化为「按全部字段判重」。
  • 未并行化（刻意）：去重结果相互依赖（“首次出现”需要全局顺序），按行块并行会破坏该语义；实测 200 万行量级耗时与筛选同阶，无需并行。
  • 重复行对应表：unique_rows_with_map 在 collect_map = true 时额外产出 (保留的首次出现行, 被剔除的重复行) 列表（默认关闭以省内存：每对约 8 字节）。去重完成后界面弹窗询问是否导出（CSV / XLSX），表中含「保留行号、被剔除行号」与判重字段取值，行号从 1 开始，便于逐条核对去重是否正确。

四、GUI 与后台线程

4.1 即时模式架构

egui 即时模式：以布尔标志控制对话框（DialogStates）。主循环每帧：poll 消息 → 菜单栏 → 控制面板 → 日志 → 中央预览 → 进度 → 对话框。

4.2 后台线程桥接（background.rs）

耗时操作（打开/筛选/拆分/导出）在后台线程执行，通过 mpsc 通道回传 BgMsg（进度 / 加载完成 / 筛选结果 / 拆分完成 / 导出完成 / 错误），UI 不阻塞。任务用 catch_unwind 包裹，任务 panic 时补发错误消息，避免 UI 永久卡在忙碌状态。

4.3 虚拟化预览表格（table.rs）

egui_extras 虚拟化表格仅渲染可见行，900 万行流畅滚动；显示行数可切换 100/1000/10000/全部；双击单元格弹出该行全部列-值详情。

4.4 界面细节

  • 加载微软雅黑/黑体中文字体，默认字号 14 便于中文阅读。
  • 加宽滚动条，避免数据预览区滚动条过窄难操作。
  • 弹出窗口位置可配置（居中/右侧/左侧/中间/记忆位置），egui persistence 记忆。
  • 进程峰值内存用 GetProcessMemoryInfo（winapi）实时显示。
  • 操作日志可选落盘（「设置 → 操作日志落盘」，默认关闭）：开启后每条日志追加写入 exe 同目录的 操作日志.txt（不可写时回退 %TEMP%），超过 2MB 自动轮转为 .1。纯文本、零依赖、可搜索，适合事后审计；开关状态经 egui memory.data 记忆。
  • 操作日志的两道护栏（为什么不需要日志数据库）：内存日志有 5000 条硬上限（超出丢弃最旧，约 0.4MB），且日志是「操作级」而非「行级」——一次千万行拆分最多也只产生 51 条（50 条逐文件行数 + 1 条汇总），日志量与数据规模无关；日志面板用 ScrollArea::show_rows 虚拟化渲染，只布局可见行。启动诊断日志（exe 同目录 csv_editor_rust.log）超过 2MB 自动轮转为 .log.1。
    结论：不引入 SQLite 等日志数据库。rusqlite 的 bundled 特性需用 C 工具链编译 SQLite，与本项目 Win7 自包含链接链（rust-lld + -C link-self-contained=yes + build-std）冲突且验证成本高；动态链接 sqlite3.dll 则在 Win7 上并不存在，会直接破坏「单文件、无外部 DLL 依赖」这一核心特性；纯 Rust 实现尚不成熟。几百到几千条日志用文本搜索已足够，数据库属于过度设计。
  • 底部状态栏（TopBottomPanel::bottom）：显示总行数 / 筛选后行数 / 列数 / 进程峰值内存，以及文件名、大小与编码。它先于右侧日志面板渲染，因此横跨窗口底部全宽。
  • 三条工具栏：主工具栏（打开/合并/导出/筛选/清除筛选/界面缩放/自愿捐助等）、「数据处理」工具栏（拆分数据、8 项列操作、撤销/恢复、清理筛选缓存、文件信息）、「数据分析」工具栏（提取唯一行/去重）。后两条由「工具 → 数据处理工具栏 / 数据分析工具栏」切换显示，默认显示；菜单项以对号标记当前状态，两态文本等长（尾部空格占位）以保证与其它菜单项左对齐、且宽度不跳动。三条工具栏都包在 ScrollArea::horizontal 中，界面放大到 1.5 倍时仍可横向滚动访问全部按钮。
  • 进度窗口必须 constrain_to(screen)：该窗口用 egui::Area 实现，而 Area 默认 constrain = false（不夹取到屏幕内），位置又取自持久化的“上次拖动位置”。界面缩放（按钮大小）或窗口尺寸变化后逻辑屏幕变小，记忆位置可能落到可视区之外，进度窗口便“消失”。对话框用 Window（默认 constrain = true）故不受影响——这正是“只有进度条不见了、对话框都正常”的原因。

4.5 IME 修补（中文输入，app::patch_ime_events）

上游缺陷（已在 headless 测试中复现）：egui 0.27.2 的 TextEdit 处理 Event::CompositionEnd(prediction) 时，要求当前光标与 state.ime_cursor_range 的 secondary 端一致才插入文本，而 ime_cursor_range 只在 CompositionUpdate 中更新。Windows 输入法连续上屏时，winit 发出的是没有 preedit 的 Ime::Commit，egui-winit 于是只推送一个 CompositionEnd，其 ime_cursor_range 仍停留在上一次的值 → 提交被静默丢弃，表现为中文只能输入第一个字，之后的字词不显示（字母/数字走 Event::Text，不受影响）。
  • 修补位置：eframe::App::raw_input_hook（egui 处理输入之前），调用 patch_ime_events(&mut raw_input.events)。
  • 修补方式：给每个“前面没有 CompositionUpdate 的 CompositionEnd”补发 CompositionStart + 空的 CompositionUpdate —— 空 preedit 不插入任何字符，只把 ime_cursor_range 同步到当前光标，随后提交即可正常落字。
  • 不含 CompositionEnd 的帧（绝大多数）直接返回，零开销；对正常 preedit 流程与字母输入无影响（均有单元测试覆盖）。
  • 之所以不能直接升级 egui：0.27 是为 Win7 兼容锁定的版本（winit 0.29 才支持 Win7）。

4.6 新增对话框与动作（多文件合并 / 使用说明 / 捐助）

  • 多文件合并对话框：文件列表（可逐项「移除」或「清空列表」）+ 一次性多选与「追加选择文件」；实时显示表头校验结论与差异字段；表头不一致时提供「只保留相同字段名」选项，条件不满足时按钮禁用并说明原因。
  • 使用说明对话框（菜单「帮助 → 使用说明」）：分十节讲解（上手三步、打开与合并、预览、筛选、拆分、列操作、导出、界面缩放、常见问题、支持开发者），以 collapsing 折叠分节。
  • 自愿捐助对话框：微信收款码用 include_bytes! 内嵌（单文件发布不能依赖外部图片），经 image crate 解码为 RGBA 后由 Context::load_texture 缓存为纹理，只解码一次。
  • 工具栏「🧹 清除筛选」与筛选窗口内的同名按钮等价（清空条件 + 回到完整数据视图），供不打开窗口时一键恢复。

4.7 界面等比缩放（按钮大小）

  • 缩放值以应用状态 ui_zoom 为唯一真值源，写入 egui::Context::zoom_factor()（egui 自带持久化，重启后仍生效）；DragValue 限制 1.0 ~ 1.5 倍、步进 0.01。同时关闭 egui 内置的 Ctrl +/- 缩放（options.zoom_with_keyboard = false），避免出现两个真值源互相覆盖。
  • 拖动时先累积、松手后应用：DragValue 以 response.drag_delta()（本帧“逻辑坐标”位移）计算数值，而 set_zoom_factor 会改变 pixels_per_point，使同一物理鼠标位置对应的逻辑坐标在一帧内突变，于是 drag_delta() 出现虚假位移、数值反向跳变并与界面来回震荡（表现为“拖动时跳动厉害”）。因此拖动期间只更新数值（并提示“松开鼠标后应用”），在 drag_stopped() 或键盘输入完成时一次性平滑应用。
  • 采用整体等比缩放而非只放大字体：数据表格行高是固定 20px，只放大文字会导致错位；整体缩放让菜单、菜单命令、工具栏按钮、表格文字同步放大，符合「等比例放大倍数」的设定。
  • 「自愿捐助」与「按钮大小」不右对齐，按顺序排在工具栏按钮之后（输入框位于「按钮大小」与「倍」之间）；由于工具栏按钮较多（放大后总宽可超过窗口宽度），整行用 ScrollArea::horizontal 包住，溢出时可横向滚动访问，保证各按钮始终可达。

五、Windows 7 单文件兼容

标准 Rust std 自 1.58+ 静态导入 Win8/Win10 API（如 GetSystemTimePreciseAsFileTime），普通编译产物在 Win7 无法加载。本项目用 Rust 官方 Tier 3 目标 x86_64-win7-windows-gnu + nightly build-std 重新编译标准库，才得到真正 Win7 兼容的产物（已验证导入表）。

5.1 关键构建参数

RUSTFLAGS=-C target-feature=+crt-static -C link-self-contained=yes -C linker=rust-lld
cargo +nightly-2025-06-23-x86_64-pc-windows-gnu build --release \
  --target x86_64-win7-windows-gnu -Z build-std=std,panic_abort
产物：target\x86_64-win7-windows-gnu\release\csv_editor_rust.exe 导入表：仅 Win7 内置系统 DLL（kernel32 / msvcrt / user32 / gdi32 / advapi32 / shell32 / ole32 / opengl32 / dwmapi / uiautomationcore 等，实测 16 个），无 UCRT、无 API-set 依赖。
资源编码（易踩）：src/icon.rc 是 UTF-8，文件头必须保留 #pragma code_page(65001)。windres 默认按本地代码页解析 .rc（中文系统为 936/GBK），缺了这行则版本信息里的中文全部乱码——exe 属性中产品名会显示成“瀹跨粡03瓒呭ぇCSV鏂囦欢瀹炵敤缂栬緫鍣”。build.rs 用 embed-resource 调 windres 且不外传代码页参数，故只能由 .rc 自身声明。

5.2 版本陷阱（实测）

  • Mesa 22.1.7（x64 mingw opengl32.dll + libgallium_wgl.dll + libglapi.dll，用系统 msvcrt 免 VC++）+ 安装 Vulkan Runtime（提供 vulkan-1.dll）→ Win7 x64 实测可运行。
  • 26.1.7 依赖 UCRT 与 Win8 的 GetSystemTimePreciseAsFileTime → 报“无法定位程序输入点”；22.1.7 静态导入 vulkan-1.dll → 不装 Vulkan 报缺失。
  • 20.3.4 / 18.1.8 的 opengl32.dll 编入 AVX/AVX512 → 无 AVX CPU（如 Core2 T7700）报 0xc000001d。
  • CPU 需支持 AVX（建议 Sandy Bridge 2011+）。
  • 依赖锁定：egui/eframe 0.27 + winit 0.29 才是 Win7 兼容版本；本地 vendor/webbrowser stub 绕开 idna/icu 的 edition2024 依赖（Cargo 1.81 不支持）。

5.3 诊断机制

release 为 GUI 子系统且 panic = "abort"（无控制台、无 stderr），任何启动错误都“无反应”。因此 main 里安装文件 logger + panic hook，把 log::error!/warn!、panic 与 run_native 返回的 Err 写到 exe 同目录 csv_editor_rust.log（不可写则回退 %TEMP%），可在 Win7 上定位真实错误（如 NoGlutinConfigs、OpenGL 版本、缺失 DLL）。

7.2 已知限制

  • 按字段拆分对唯一值超过 20,000 个的字段会拒绝（提示改用按行数拆分），避免生成海量文件。
  • XLSX 导出超 1,048,576 行自动分 sheet；列数超 16,384 报错改用 CSV。
  • XLSX 为全文本导出：所有单元格按文本写入（Excel 中数字左对齐、不参与求和等数值计算），以此换取长数字、前导零与大整数的零精度损失。
  • UTF-16 文件整体转码载入内存（此类文件通常较小）；超大 UTF-16 建议先转码。

一、项目概览

原 Python/PyQt6 工具（1.3_nodask.py，4227 行）的 Rust 重构，专注超大 CSV 文件的读取、预览、筛选、拆分、列操作、哈希、统计分析（去重 / 分组汇总 / 列统计 / 频次分布 / 重复情况 / 数据质量 / 透视表 / 交叉统计）与导出。实测可处理 6.5GB / 901 万行 / 55 列 的数据，打开约 4 秒、峰值内存约 148MB，最终产物为兼容 Windows 7 的单文件 exe（约 7.4MB，无外部 DLL 依赖）。

二、分层架构

核心原则：数据引擎（core）与 GUI 层严格分离，core 无任何 GUI 依赖，可独立编译、单元测试与命令行调用。

三、核心引擎设计

3.1 读取器（reader.rs + csv.rs）

  • mmap 内存映射文件（不载入内容，仅映射虚拟地址空间）。
  • 流式行索引：分块顺序读文件构建行偏移索引（build_index_streaming），不触碰 mmap 页，避免把 6.5GB 文件整体拉入工作集 —— 这是内存降低两个数量级的关键。
  • 引号感知：CSV 状态机（csv.rs）处理双引号包裹字段、字段内换行、"" 转义、CRLF / CR / LF 换行。
  • 惰性字段访问：按 (行, 列) 取原始字节，仅在需要时解码为 UTF-8。行偏移索引内存约 8B/行，O(行数)。
  • UTF-16 文件在字节级无法安全切分（分隔符含 0x00），打开时整体转码为 UTF-8 再走统一路径。

3.2 编码检测（encoding.rs）

修正 Python 版“chardet + GB18030 优先”会把 UTF-8 文件误判为 GB18030 产生乱码的问题。改为严格验证优先：

BOM → 严格 UTF-8 验证 → UTF-16 启发式 → GB18030 兜底
UTF-8 是自校验编码，严格验证可靠；GBK/GB2312 等必然通过不了 UTF-8 验证而正确落到 GB18030 超集。所有数据内部统一为 UTF-8 String。

3.3 数据模型（model.rs）— 全文本模式

  • 所有列一律视为文本（TypeKind::Text），避免数值类型影响导出，保证长数字 / 前导零 / 大整数不丢精度。
  • classify 保留用于诊断/测试（整数 ≤18 位、浮点、>18 位长数字 → 文本、特殊浮点文本），不再参与导出类型判断。
  • row_into 复用目标容量，避免大数据逐行遍历时的字符串分配。默认采样 DEFAULT_SAMPLE_ROWS = 1000。

3.4 筛选引擎（filter.rs）

  • 10 种条件：等于/包含/不包含/大于/小于/大于等于/小于等于/不等于/空值/非空值；条件间用且/或组合，AND 短路。
  • 数值比较优先：整数用 i128 精确比较（覆盖 19 位卡号），浮点回退 f64；双方均可数值化时数值比较，否则字符串比较（trim 后）。
  • 并行分块评估（std::thread::scope），进度回调；并行度上限 MAX_FILTER_THREADS = 32。实测 200 万行 × 15 列（326MB）：单条件 0.046~0.057 秒。
  • 整行只解析一次（RowReader）：线程局部的行读取器把本行所需列的文本写进复用 String，同一行的多个条件共享这一次解析。此前每个条件各调一次 model.field(row, col)，每次都重新解析整行并分配 Vec<Vec<u8>>、每字段一个 Vec<u8> 与一个 String——条件越多重复解析越多，而且即使只取一列也要解析全部列。
  • 底层解析用零分配的 csv::parse_record_into（复用内容缓冲 + 字段偏移表），与 parse_record 语义一致，并有逐字段一致性测试守护（覆盖引号、"" 转义、空字段、字段内换行、中文字段等边界）。
  • 实测（优化前 → 优化后，同机同期、重复 3 次取最小）：1 条件 0.258s → 0.051s（并行度 12.8 → 27.0）；5 条件混合 0.297s → 0.057s；CPU 时间 3.3s → 1.4s。
  • 结果行号用 u32（支持 ≥43 亿行）。

3.5 拆分引擎（split.rs）

  • 按字段拆分单遍哈希分组 O(N)，消除 Python 版 df[df[col]==value] 的 O(N×U) 重复全表扫描。
  • 文件数上限保护 MAX_SPLIT_FILES = 20000；重名文件自动追加序号（Python 版直接覆盖）。
  • 文件名清洗：替换 Windows 非法字符与控制字符、压缩连续下划线、按字符边界截断 100 字符。
  • 多列组合键用 \x1F 连接，避免歧义。
  • 按行数拆分：并行写出。各批的行区间与输出文件彼此独立，按批号用原子计数分派给工作线程；并发度取核数但不超过 8（拆分是 IO 密集型，同时打开过多输出文件在机械盘/网络盘上会因寻道竞争变慢）。实测 200 万行 × 15 列（326MB）：4.61s → 0.66s，并行度 1.00 → 7.15。
  • 按字段拆分 XLSX：第二阶段并行转换。两阶段拆分中「中间 CSV → XLSX」的各分组相互独立，可安全并行；并发度上限取 6，因为每个转换会把该分组的全部单元格驻留内存，同时进行过多会显著抬高进程峰值内存。实测 47.66s → 18.27s，并行度 0.97 → 3.72。
  • 按字段拆分（CSV）仍为单线程，这是刻意取舍：它要求“每个分组内的行序与源文件一致”，并行写同一文件会打乱顺序；可行的并行化要么两遍扫描（先算 key 再随机读回），要么按块切分临时文件再合并（临时文件数 = 块数 × 分组数），代价与收益不成比例。该路径只做单线程内的开销优化：分组 key 写入复用缓冲，命中已有分组时用 &str 借用查询（HashMap<String, _> 实现 Borrow<str>），只有首次出现新分组才 clone 一份 owned key（实测 5.62s → 5.28s）。
  • CSV 写出路径：CsvWriter::write_row 需要引号时按引号位置分片写出（早期实现是逐字节 write_all）。两条实测教训：不要在中间 Vec 里拼整行再写出（多一次整行拷贝，按字段拆分反而慢 14%）；needs_quote 保持用 str::contains（底层 memchr），改成手写逐字节扫描会慢约 7%。
  • 拆分完整性核对：每次拆分后，各输出文件会被读回重新统计数据行数（count_data_rows：流式、引号感知、不建索引，对超大文件也只是一次顺序读），与写入时累计的行数逐文件对照，并统计「全部输出合计」是否等于「数据来源行数」；结论写入操作日志（逐文件行数 + 合计 + 核对通过/未通过）。XLSX 两阶段模式下核对的是「转换时读回的中间 CSV 行数」，XLSX 自身的行数由写出 API 逐行写入保证。相关测试：count_data_rows_is_quote_aware、split_report_reconciles_row_counts。
  • 拆分完整性核对表：拆分完成后在输出目录自动写出 拆分完整性核对表_<时间戳>.csv（如 拆分完整性核对表_2026-09-27_100500.csv；utf-8-sig，Excel 可直接打开）。文件名带时间戳，因此后一次拆分不会覆盖上一次的核对表，便于按时间归档比对。内容包括：拆分类型、拆分依据、输出格式、核对方式、数据来源行数、输出文件数、输出总行数、完整性核对结果，以及逐文件的「数据行数 / 写入行数」明细与合计行。相关测试：checkfile_contains_all_required_items。
  • XLSX 输出的核对方式：CSV 输出会读回文件重新统计行数（count_data_rows，引号感知）作为核对依据；XLSX 是 zip 压缩容器，用「按换行统计行数」的方式读回必然得出错误结果（曾导致结果正确却误报「完整性核对未通过」），因此 XLSX 的行数取自写入统计——写入逐行进行、任何失败都会返回错误，故该值可信——并在报告与核对表中如实标注「未读回验证」。按字段拆分的 XLSX 走两阶段，核对的是转换时读回的中间 CSV 行数。相关测试：split_by_rows_xlsx_report_is_complete。
  • 性能基准：src/bin/split_bench.rs（cargo run --release --bin split_bench -- [行数] [重复次数]），输出各场景墙钟耗时、进程 CPU 时间与平均并行度（CPU/墙钟，≈1.0 即单核）。单次测量有 ±10% 抖动，故默认重复 3 次取最小值。

3.6 列操作 / undo-redo（column_ops.rs）

Python 版每次操作 df.copy(deep=True) 深拷贝整表 + 20 步历史，6.5GB 数据单次拷贝即 OOM。
  • 本引擎以操作描述（派生列 DerivedColumn）记录，零复制零物化；字段在访问时按需计算。
  • 删除/隐藏为视图层操作（不物理重写 900 万行数据）。
  • undo/redo 为命令式栈：undo 弹出并反向执行，redo 重放，同样零复制。
  • 派生列类型：SplitField / Merge / Copy / Constant / Hash。

3.7 导出引擎（export.rs）

  • CSV：utf-8-sig（带 BOM） 流式写出，与 Python 版一致。
  • XLSX：超过 XLSX_MAX_ROWS_PER_SHEET = 1_048_576 自动分 sheet（Python 版直接崩溃）；超过 Excel 上限 16384 列则报错改用 CSV。
  • 全文本导出：所有列一律按文本（@ 格式）写入，长数字 / 前导零 / 大整数不会被 Excel 数值化，从根本上杜绝科学计数法与精度丢失（不再依赖“列名关键词 + 数据采样”的启发式长数字列识别）。
  • 公式注入防护（CWE-1236）：以 = + - @ 开头的字段加 ' 前缀；内部中转文件用 new_raw 关闭。

3.8 多文件合并（merge.rs）

  • 表头校验前置：read_file_header 只读文件开头（最长 64KB），按检测到的编码解码后取第一行解析，不构建行索引；否则 CsvFile::open 对 6.5GB 文件每个要约 4 秒，选十几个文件校验就要一分钟。
  • 一致性判定：check_headers 分三档——完全一致 / 字段相同仅顺序不同 / 存在字段名差异；差异字段名由 exclusive_fields 列出，供界面提示。
  • 按字段名对齐：合并时建立「目标列 → 源文件列」映射（按名称 position 查找）而非按位置拼接，因此各文件列顺序不同也能正确合并，源文件缺列写空值。
  • 共有字段交集：表头不一致时按用户选择取 common_fields（首个文件顺序去重后的交集）。
  • 流式写出：输出 utf-8-sig CSV，用 CsvWriter::new_raw（不加公式注入的 ' 前缀）——合并结果是数据而非 Excel 导出目标，加前缀会污染负数、加号开头的字段。
  • 合并结果写入临时文件后按普通单文件打开，从而复用筛选 / 拆分 / 列操作 / 导出的全部能力；再次合并前会清理上一个临时文件。

3.9 去重引擎（dedup.rs）

  • 语义：在传入的行集合（界面传当前筛选结果，未筛选时为全部数据）内，按 key 列的值组合判断重复，保留每条重复记录中首次出现的行，因此结果行序与输入一致。
  • key 拼接用  分隔：避免 ("ab","c") 与 ("a","bc") 被判为同一行（有专门测试守护）。
  • 零分配逐行处理：复用筛选同款 RowReader（整行只解析一次、字段文本零分配），key 也用同一个复用 String 构建；命中已有 key 时以 &str 查询去重表，只有新唯一行才 clone 一份 key。
  • 越界列容错：丢弃超出当前列数的字段索引（界面可能传入陈旧索引），全部越界时退化为「按全部字段判重」。
  • 未并行化（刻意）：去重结果相互依赖（“首次出现”需要全局顺序），按行块并行会破坏该语义；实测 200 万行量级耗时与筛选同阶，无需并行。
  • 重复行对应表：unique_rows_with_map 在 collect_map = true 时额外产出 (保留的首次出现行, 被剔除的重复行) 列表（默认关闭以省内存：每对约 8 字节）。去重完成后界面弹窗询问是否导出（CSV / XLSX），表中含「保留行号、被剔除行号」与判重字段取值，行号从 1 开始，便于逐条核对去重是否正确。

3.10 统计分析引擎（stats.rs）— 字段分组汇总

  • 语义：在传入的行集合（界面传当前筛选结果，未筛选时为全部数据）内，按 1~3 个字段的取值组合分组，对指定列做聚合 —— 每组自动给出行数，并对每个「列 × 聚合方式」产出：求和、均值、最大、最小、计数（非空）、去重计数、空值数。
  • 输出顺序 = 分组在行序中首次出现的顺序（稳定、可复现）。分组 key 用 \x1F 连接（与 split.rs/dedup.rs 同一约定），还原分组值时用 splitn 限制段数，字段值里即使出现分隔符也能正确切分。
  • 可交换聚合 → 并行：聚合满足结合律，因此采用「按行块并行局部聚合 + 按块序合并」，与筛选（并行扫描但要保序输出）不同，这是统计在性能上的优势。并行度上限 MAX_STATS_THREADS = 32；各线程用 RowReader 零分配逐行取值，块内用 HashMap<key, 局部acc>，合并时新 key 追加到末尾 —— 因此合并顺序即全局首次出现顺序。
  • 数值语义与筛选完全一致：直接复用 filter.rs 的 try_num/cmp_num（在 filter.rs 中改为 pub(crate)），避免两处各写一套解析与比较而漂移。
  • 求和的精度：定点十进制累加（不是 f64 累加）。把每个数值按小数位数放大成 i128 整数再相加（parse_dec + fmt_dec，小数位数上限 DEC_MAX_SCALE = 9），因此 1000000000.01 这类金额能被精确表示；若改用 f64 累加，几百次相加后就会跑出 3613134567.580001 这样的尾巴（用户实测反馈，已修复，回归测试 sum_has_no_f64_accumulation_noise 里用朴素 f64 累加作对照）。合并并行分块的局部和时按小数位数对齐后再相加（测试 sum_merges_blocks_with_different_scales）。只有当某个值无法用十进制字面量精确表示时才整体回退 f64：科学计数法（1e5）、超过 9 位小数、超过 30 位数字（sum_falls_back_for_non_decimal_values）。均值 = 精确和 ÷ 非空计数，仍是 f64 除法（保留 6 位小数）。
  • 非数值单独计数：非空但无法解析为数值的值（如「未知」）不计入求和/均值，而是单独计数，并在界面与日志中提示；「最小/最大」见下一条。
  • 规模上限可调（StatsLimits）：max_groups（分组数，也用作交叉统计的 A 侧取值上限）、median_budget（列统计的精确中位数数值预算，按列数均分）、freq_budget（频次分布的不同取值预算）、max_dup_keys（重复情况的不同键上限）、max_cross_pairs（交叉统计的组合数上限）—— 默认值就是各功能原先的硬编码值，界面在对应参数窗底部提供 DragValue 调整并写入 egui::memory（Id::new("stats_limits")）以便重启沿用；超限报错都提示「调大上限 / 减小统计维度 / 先筛选」。实现上各功能保留原签名（内部委托默认上限），另提供 *_with_limits 入口供界面调用，避免大规模改动既有测试。
  • 「最小/最大」的文本回退（用户实测反馈）：累加器在遇到非数值时额外记录文本极值（update_text_extremes，命中时借用比较并复用 String 容量，不额外分配；并行合并用 merge_text_extremes，每线程/每分块 O(1) 空间）。输出规则：该列只要有一个可解析数值就按数值比较（行为与以前一致），整列都没有数值时才退化为字典序最小/最大。
    动机：交易时间（2026-01-05 10:30:00）这类列解析不成数值，此前"最大/最小"永远是空的，而用户恰恰要用它找"开始/结束时间"；定长日期时间文本的字典序即时间先后，因此直接取文本极值就能得到最早/最晚。分组汇总、列统计（ColAcc）、透视表（复用同一 Acc）三处共用该逻辑，notes 里会写明"按文本顺序比较"。
  • 内存与规模护栏：分组数上限 MAX_GROUPS = 20000（超出则报错并提示改用取值较少的字段，与拆分同思路）；单个「去重计数」最多保存 MAX_DISTINCT_VALUES = 200000 个不同值，超出后结果标注为 >=N 而不是静默膨胀（去重计数按值集合实现，是唯一不满足 O(1) 空间的聚合）。
  • 派生列不参与统计：统计走 RowReader 的原列零拷贝读取，因此只接受原始列（界面按 ColumnOps::view_to_base 过滤派生列）；越界/陈旧的列索引一律丢弃，全部无效时报错。
  • 参数校验由引擎负责：无有效分组字段、无有效聚合列、分组数超限都返回明确的错误信息，界面只负责把错误写进操作日志。
  • 性能实测（本机 32 逻辑核，200 万行 × 15 列 / 326MB，重复 3 次取最小）：1 字段分组（20 组）× 求和/均值/最大/最小 0.081s（并行度 25.1）；× 计数/空值数 0.056s（26.3）；2 字段分组（100 组）0.073s（22.6）；3 字段分组（700 组）0.080s（19.0）；含去重计数的 6 聚合列 1.009s（3.8，瓶颈是合并阶段单线程对 HashSet 的并集）。求和的定点解析让「求和类」场景比纯 f64 累加多约 0.015s（精度换来的、可接受的代价）。基准程序 src/bin/stats_bench.rs。
  • 结果去向：结果表（StatsTable：表头 + 行 + 输入行数/分组数/非数值计数）在结果窗中虚拟化展示（复用预览表的 TableBuilder 经验与 truncate_cell），并可直接导出 CSV（utf-8-sig + 公式注入防护）或 XLSX（全文本、超 104 万行自动分 sheet）—— 复用 export.rs 的 export_rows_csv/xlsx，导出同样走后台线程 + 进度 + BgMsg::ExportDone。统计不改变当前数据视图（与去重不同：去重会把结果作为新的当前视图）。
  • 可核对性：e2e 端到端回归把「各组行数之和 == 统计范围行数」作为内置一致性检查，并导出统计结果 CSV/XLSX 各一份供人工抽查。

3.11 数值列统计（stats.rs::describe_columns）

  • 指标：对每个选定列给出 行数、计数（非空）、空值数、非数值数、求和、均值、中位数、最小、最大、标准差（每列一行，导出即一张表）。
  • 一次扫描算完所有列：与分组汇总同款「按行块并行 + 按块合并」，每线程持有一组线程局部的 ColAcc；不按列反复读表（否则 N 列就是 N 遍全表解析）。
  • 求和/均值分子复用同一套定点十进制累加（DecSum），因此金额列不会出现 f64 尾差；均值分母是数值个数（非数值不计入，见下）。
  • 标准差用 Welford 在线算法（mean + M2），避免 Σx² − n·mean² 在数值大时的灾难性抵消；分块合并用 Chan 公式的稳定形式 mean += δ·n₂/n。踩过的坑：教科书形式 (n₁·m₁ + n₂·m₂)/n 即使两边均值完全相同，也会因 n₁·m₁ 的舍入让均值漂移，进而让 M2 凭空增长——同一数值重复 40 万次本应得到标准差 0，却会算出 2.09e-7（已修复，测试 column_summary_exact_sum_and_std_dev）。输出为总体标准差（分母 n），并在结果表 notes 里说明换算样本标准差的方法。
  • 中位数必须保留原始数值，所以是本功能唯一有内存预算的部分：单列上限 MEDIAN_MAX_PER_COLUMN = 10_000_000（80MB）、总预算 MEDIAN_TOTAL_BUDGET = 20_000_000（约 160MB）按列数均分（下限 MEDIAN_MIN_PER_COLUMN = 200_000）。某列数值个数超过保留上限时，中位数输出 — 并在 notes 里给出「数值 N 个，超过上限 M」——不静默给近似值（与 XLSX 核对「未读回验证」同样的诚实标注思路）。精确性判据是 values.len() == numeric，合并时若任一侧已不完整就停止拼接。
  • NaN / ±inf 不算数值：与 model::classify 的判定一致，计入非数值数（否则会把均值/标准差污染成 NaN）。分组汇总的数值聚合同步采用该判定。
  • 「计数」与「数值个数」是两个概念：计数 = 非空值个数（含文字），数值个数 = 可解析为数值的个数（均值/中位数的基数）。分组汇总的均值也改用数值个数作分母（此前用非空个数，含文字时均值会偏低）。
  • 性能实测（200 万行 × 15 列 / 326MB，本机 32 逻辑核，重复 3 次取最小）：1 列（金额）0.091s（并行度 15.6）、4 列 0.125s（17.5）、10 列 0.158s（18.4）——中位数排序在块合并后单线程做，重复值多时很快。
  • 结果去向：与分组汇总共用同一个结果窗（虚拟化表格 / 最小化 / 导出 CSV、XLSX）与同一份 StatsTable 结构（kind 区分标题与导出文件名，notes 承载提示）；e2e 也加了「计数 + 空值数 == 行数」的一致性核对。

3.12 取值频次分布 / Top-N（stats.rs::value_frequency）

  • 指标：选定列各取值的 出现次数 与 占比(%)，按次数降序取前 N（默认 20，界面可调到 1000，引擎侧再兜底 MAX_FREQ_TOP_N）；结果表列固定为 列名 / 排名 / 取值 / 出现次数 / 占比(%)，多列时按列分段，一次扫描算完所有列。
  • 占比按 4 位有效数字输出（去掉尾随零）：fmt_pct 按 floor(log10) 推算所需小数位（decimals = 3 − exp，上限 12），得到 50 / 33.33 / 0.0475 / 0.004748 这类结果。踩过的坑（用户实测反馈）：最初用固定 2 位小数（{:.2}），115 万行的频次表里"出现 95 次"与"出现 55 次"分别显示为 0.01 / 0.00，相邻名次完全无法区分 —— 低频占比必须按有效数字显示（回归测试 fmt_pct_keeps_four_significant_digits，含 55/1158418 → 0.004748 的真实用例）。
  • 每列末行是「(合计)」：出现次数 = 该列各取值计数之和（等于统计范围行数）、占比 100%，用于直观核对"总量对得上"；e2e 同时校验「各取值行的次数之和 == 统计范围行数」与「合计行 == 统计范围行数」。逐行占比因舍入相加可能略偏离 100%，合计行给的是精确值，notes 中也写明了这一点。
  • 排序规则：次数降序，次数相同按取值升序 —— 结果稳定、可复现（frequency_ranks_by_count_desc_then_value 守护）。
  • 空值也是一类：trim 后为空的行计入 (空)，参与排名与占比（数据质量信息不该被丢掉）；占比分母是统计范围行数（含空值行），因此各列各行的占比之和恒为 100%。
  • 「(其余 M 个取值)」行：超出 Top-N 的取值不逐个列出，而是汇总成一行（次数与占比合计），这样结果表既短又不丢总量 —— 拿着结果做"各类占比"的核对也不会漏项（frequency_top_n_truncates_with_rest_row 里断言「次数合计 == 统计范围行数」）。
  • 按原值统计（不 trim、区分大小写，与去重判重一致）：北京 与 北京␣ 是两个取值。与筛选的"等于"（trim 后比较）不同，这是刻意的：频次分布要如实反映原始写法。
  • 内存护栏与"拒绝而非近似"：不同取值总数预算 FREQ_TOTAL_BUDGET = 3_000_000（按列数均分，单列上限 FREQ_MAX_PER_COLUMN = 1_000_000，下限 200_000）。块内与合并阶段都内存有界：达到上限后只置超限标记、不再插入新键（已有键继续计数），扫描结束后统一报错，提示「先用筛选缩小范围，或减少一次统计的列数」。为什么报错而不是给近似结果：Top-N 依赖完整计数 —— 若丢弃了后面的取值，某个实际出现 500 次的值可能被忽略，而结果里"最高频 300 次"的结论就是错的。宁可拒绝，也不给会误导人的表（基准里专门有一条"预期拒绝"场景演示该护栏）。
  • 性能实测（200 万行 × 15 列 / 326MB，32 逻辑核，重复 3 次取最小）：1 列（20 个取值）0.041s（并行度 24.1）、3 列（620 个取值）0.052s（20.3）、5 列 Top-20 0.064s（21.1）、5 列 Top-1000 0.064s（21.9）；高基数列（账号 200 万唯一值）在 0.56s 触达上限并拒绝。
  • 可核对性：e2e 增加频次分布步骤，内置「各行的出现次数之和 == 统计范围行数」与「合计行 == 统计范围行数」核对，并导出 CSV/XLSX 供人工抽查。

3.13 重复情况统计（stats.rs::duplicate_stats）

  • 定位：与「提取唯一行（去重）」互补 —— 去重是"把重复去掉"，这里是"把重复看清楚"：哪些键重复、各重复几次、重复行占比，并能把结果一键落回当前视图。
  • 与去重共用判重口径：同一套键构建规则（\x1F 连接、按原值比较、越界列丢弃、空列集合表示"全部字段"）、同样保留首次出现；因此 DuplicateReport::unique_rows 与 dedup::unique_rows 的输出逐行相同 —— 有专门测试（duplicate_stats_matches_dedup_engine）交叉验证两套实现，防止日后改动让二者漂移。
  • 输出：汇总数字（统计范围行数、不同键数、重复键数、重复行数、重复率）+ 明细表（每个重复键一行：判重字段取值… / 出现次数 / 重复行数 / 占行数(%) / 首次出现行号，按重复次数降序），另有可直接落回视图的 dup_rows 与 unique_rows。
  • dup_rows 与 duplicate_rows 的区别（易混）：duplicate_rows 是"多出来的行数"= 统计范围 − 不同键；dup_rows 是"重复键涉及的全部行"（含首次出现的那行），因为「只看重复的行」时要把首次出现那行一起显示出来才能逐条对比。两者都写进了 notes。
  • dup_rows 按重复键分组排列（用户实测反馈后改进）：组间顺序与明细表一致（重复次数降序、次数相同按键升序），组内按行号升序。这样落回预览区后同一个键的各行紧挨着 —— 否则按原始行号升序排列时，同一键的行会被其它键的行隔开（如 A 在 1、500 行，B 在 2、300 行，显示成 1/2/300/500 根本看不出配对）。行号列仍是原始行号，便于回原表核对；预览表按传入的行序渲染，无需额外改动。回归测试 duplicate_stats_keeps_same_key_rows_adjacent 用一个"组号单调不减"的断言守护该顺序。
  • 内存护栏：不同键上限 MAX_DUP_KEYS = 2_000_000，超出报错并提示先筛选缩小范围或减少判重字段。
  • 单线程（刻意）：键表需要全局唯一、首次出现行号依赖全局顺序，与去重同理；实测 200 万行按 1~2 列判重 0.56~0.75s，按整行（15 列、200 万键）2.65s。
  • 可核对性：e2e 校验两条恒等式 —— 「不同键 + 重复行 == 统计范围行数」与「重复涉及行 ∪ 唯一行 == 统计范围全部行」，并导出明细 CSV/XLSX。

3.14 空值与数据质量统计（stats.rs::describe_quality）

  • 指标（每列一行）：行数、空值数、纯空白数、空值率(%)、含控制字符数、最短长度、最长长度、平均长度、超长值数(>255 字符)。
  • 口径：空值数 = 长度为 0；纯空白数 = trim 后为空但长度 > 0；空值率 = (空值数 + 纯空白数) ÷ 行数（业务上"只有空白"通常等同于空，故合并计率）；含控制字符数 = 值里出现 char::is_control() 的行数（含制表符 \t、字段内换行、0x7F）—— 银行 CSV 的尾随制表符会在这里显形；长度按字符数（中文算 1 个）统计，最短/最长/平均只算非空值；超长值数 = 字符数 > LONG_VALUE_LEN = 255 的个数。
  • 一次并行扫描（与列统计同款按行块并行 + 按块合并），每列只维护 O(1) 状态，不保留原始值；每个值只做一次 chars() 遍历同时得到长度与"是否含控制字符"（避免两次扫描）。
  • 汇总提示：结果表的 notes 会给出「共 N 列：其中 M 列存在空值或纯空白、K 列含控制字符、J 列有超长值」，让用户一眼找到需要清洗的列。
  • 性能实测（200 万行 × 15 列 / 326MB）：5 列 0.063s（并行度 22.8）、15 列（全部）0.114s（22.4）。
  • 可核对性：e2e 重算「空值率 == (空值数 + 纯空白数) ÷ 行数」并校验「最长长度 ≥ 最短长度」，再导出 CSV/XLSX。

3.15 透视表（stats.rs::pivot_table）

  • 结构：行 = 行字段（1~2 个）的取值组合，列 = 列字段的各个取值，单元格 = 各指标（值列 × 聚合方式）在某组合下的聚合；输出「行字段… + 各列取值 + (合计)」，末行为逐列合计行。
  • 一次可放多项指标（用户诉求）：`values: &[PivotValue]`，每项 = 值列 + 聚合方式，最多 PIVOT_MAX_VALUES = 12 项，重复项自动去重。表头规则：只有一项指标时保持简洁（直接用列取值 + (合计)，向后兼容），多项时用 列取值-值列(聚合)（如 01-交易金额(求和)），合计列是 (合计)-值列(聚合)。每个格子的聚合器是一个 Vec<Acc>（与指标一一对应）。
  • 规模上限可调（用户诉求）：PivotLimits { max_rows, max_columns, max_cells } 由调用方传入，默认值 PIVOT_DEFAULT_MAX_ROWS = 20000 / PIVOT_DEFAULT_MAX_COLUMNS = 200 / PIVOT_DEFAULT_MAX_CELLS = 500000；界面在参数窗底部提供三个 DragValue + 「恢复默认」，并把设置写进 egui::memory（Id::new("pivot_limits")）以便重启后沿用，同时按「格子数 × 指标数 × ~100B」实时给出粗估内存。三处超限的报错都提示「调大上限 / 减少行字段 / 先筛选」，不再只有"改用其它工具"一条路。
  • 合计是"整体聚合"而不是"行相加"：每个单元格、每个行末合计、每个列合计、总计各自持有独立的聚合器（复用 Acc），因此均值/计数这类非可加指标在合计处依然正确——若图省事把各行数值相加，均值合计会变成"各均值的和"（明显错误）。测试 pivot_table_average_total_is_overall_not_sum_of_rows 专门守护这一点。
  • 空单元格不写 0：该行×列组合没有数据时留空，与"聚合结果恰好是 0"区分开（判断数据是否缺失时很关键）。
  • 列顺序按取值升序（稳定、可预测；日期字符串升序即时间顺序），空值是「(空)」列；行顺序为行键首次出现顺序（与分组汇总一致）。
  • 不支持「去重计数」：它要求每个格子维护一个值集合，内存不可控，引擎直接拒绝并提示改用「字段分组汇总」按两个字段分组（那里支持去重计数）。
  • 单线程：需要"行 → 单元格 → 列"三级映射，且列集合是动态增长的；实测 200 万行 × 15 列：20 行 × 100 列（1 项指标）0.85s、5 项指标（506 列输出）2.38s。
  • 可核对性：e2e 用求和聚合校验「合计行的每个单元格 == 该列各行单元格之和」，并导出 CSV/XLSX。

3.16 交叉/关联统计（stats.rs::cross_stats）

  • 回答的问题：「同一卡号对应多少个账号」「同一 IP 对应多少个证件」这类字段间对应关系，是数据关联性排查的常用手段（也用于判断两张表能否安全 join）。
  • 实现：一遍扫描同时维护 A → (行数, B 取值集合) 与 B → A 取值集合；由两侧"最大对应数"判定关系：(一对多?, 多对一?) → 一对一 / 一对多 / 多对一 / 多对多。命中已有取值时用 &str 借用查询（contains 先判），避免每行都分配 String。
  • 明细按「对应 B 的不同值数」降序（最"发散"的 A 排最前，通常就是排查重点），并列时按行数降序、取值升序；每行给出 B 取值示例（最多 CROSS_SAMPLE_MAX = 5 个，超出只显示前几个与总数）。
  • 口径与护栏：按原值比较（与去重一致），空值作为一种正常取值（示例里显示 (空)）；A 的不同取值 ≤ MAX_GROUPS、不同 (A,B) 组合 ≤ MAX_CROSS_PAIRS = 1_000_000；单线程（需要双向映射）。
  • 结果呈现：关系判定摘要放在结果表 notes 的首条，因此打开结果窗第一眼就能看到「一对一 / 一对多 / 多对多」。
  • 可核对性：e2e 校验两条恒等式 —— 明细各行「对应 B 的不同值数」之和 == 组合数、明细各行「行数」之和 == 统计范围行数（明细未截断时）。
  • 性能实测：200 万行 × 15 列下，银行×城市（20×100）0.58s、城市×备注1（100×7）0.60s；高基数列（账号做 A）在 0.02s 内被上限拦下。

四、GUI 与后台线程

4.1 即时模式架构

egui 即时模式：以布尔标志控制对话框（DialogStates）。主循环每帧：poll 消息 → 菜单栏 → 控制面板 → 日志 → 中央预览 → 进度 → 对话框。

4.2 后台线程桥接（background.rs）

耗时操作（打开/筛选/拆分/导出）在后台线程执行，通过 mpsc 通道回传 BgMsg（进度 / 加载完成 / 筛选结果 / 拆分完成 / 导出完成 / 错误），UI 不阻塞。任务用 catch_unwind 包裹，任务 panic 时补发错误消息，避免 UI 永久卡在忙碌状态。

4.3 虚拟化预览表格（table.rs）

egui_extras 虚拟化表格仅渲染可见行，900 万行流畅滚动；显示行数可切换 100/1000/10000/全部；双击单元格弹出该行全部列-值详情。

4.4 界面细节

  • 加载微软雅黑/黑体中文字体，默认字号 14 便于中文阅读。
  • 加宽滚动条，避免数据预览区滚动条过窄难操作。
  • 弹出窗口位置可配置（居中/右侧/左侧/中间/记忆位置），egui persistence 记忆。
  • 进程峰值内存用 GetProcessMemoryInfo（winapi）实时显示。
  • 操作日志可选落盘（「设置 → 操作日志落盘」，默认关闭）：开启后每条日志追加写入 exe 同目录的 操作日志.txt（不可写时回退 %TEMP%），超过 2MB 自动轮转为 .1。纯文本、零依赖、可搜索，适合事后审计；开关状态经 egui memory.data 记忆。
  • 操作日志的两道护栏（为什么不需要日志数据库）：内存日志有 5000 条硬上限（超出丢弃最旧，约 0.4MB），且日志是「操作级」而非「行级」——一次千万行拆分最多也只产生 51 条（50 条逐文件行数 + 1 条汇总），日志量与数据规模无关；日志面板用 ScrollArea::show_rows 虚拟化渲染，只布局可见行。启动诊断日志（exe 同目录 csv_editor_rust.log）超过 2MB 自动轮转为 .log.1。
    结论：不引入 SQLite 等日志数据库。rusqlite 的 bundled 特性需用 C 工具链编译 SQLite，与本项目 Win7 自包含链接链（rust-lld + -C link-self-contained=yes + build-std）冲突且验证成本高；动态链接 sqlite3.dll 则在 Win7 上并不存在，会直接破坏「单文件、无外部 DLL 依赖」这一核心特性；纯 Rust 实现尚不成熟。几百到几千条日志用文本搜索已足够，数据库属于过度设计。
  • 底部状态栏（TopBottomPanel::bottom）：显示总行数 / 筛选后行数 / 列数 / 进程峰值内存，以及文件名、大小与编码。它先于右侧日志面板渲染，因此横跨窗口底部全宽。
  • 三条工具栏：主工具栏（打开/合并/导出/筛选/清除筛选/界面缩放/自愿捐助等）、「数据处理」工具栏（拆分数据、8 项列操作、撤销/恢复、清理筛选缓存、文件信息）、「数据分析」工具栏（提取唯一行/去重、分组汇总、数值列统计、频次分布、重复情况、数据质量、透视表、交叉统计）。后两条由「工具 → 数据处理工具栏 / 数据分析工具栏」切换显示，默认显示；菜单项以对号标记当前状态，两态文本等长（尾部空格占位）以保证与其它菜单项左对齐、且宽度不跳动。三条工具栏都包在 ScrollArea::horizontal 中，界面放大到 1.5 倍时仍可横向滚动访问全部按钮。
  • 进度窗口必须 constrain_to(screen)：该窗口用 egui::Area 实现，而 Area 默认 constrain = false（不夹取到屏幕内），位置又取自持久化的“上次拖动位置”。界面缩放（按钮大小）或窗口尺寸变化后逻辑屏幕变小，记忆位置可能落到可视区之外，进度窗口便“消失”。对话框用 Window（默认 constrain = true）故不受影响——这正是“只有进度条不见了、对话框都正常”的原因。

4.5 IME 修补（中文输入，app::patch_ime_events）

上游缺陷（已在 headless 测试中复现）：egui 0.27.2 的 TextEdit 处理 Event::CompositionEnd(prediction) 时，要求当前光标与 state.ime_cursor_range 的 secondary 端一致才插入文本，而 ime_cursor_range 只在 CompositionUpdate 中更新。Windows 输入法连续上屏时，winit 发出的是没有 preedit 的 Ime::Commit，egui-winit 于是只推送一个 CompositionEnd，其 ime_cursor_range 仍停留在上一次的值 → 提交被静默丢弃，表现为中文只能输入第一个字，之后的字词不显示（字母/数字走 Event::Text，不受影响）。
  • 修补位置：eframe::App::raw_input_hook（egui 处理输入之前），调用 patch_ime_events(&mut raw_input.events)。
  • 修补方式：给每个“前面没有 CompositionUpdate 的 CompositionEnd”补发 CompositionStart + 空的 CompositionUpdate —— 空 preedit 不插入任何字符，只把 ime_cursor_range 同步到当前光标，随后提交即可正常落字。
  • 不含 CompositionEnd 的帧（绝大多数）直接返回，零开销；对正常 preedit 流程与字母输入无影响（均有单元测试覆盖）。
  • 之所以不能直接升级 egui：0.27 是为 Win7 兼容锁定的版本（winit 0.29 才支持 Win7）。

4.7 界面等比缩放（按钮大小）

  • 缩放值以应用状态 ui_zoom 为唯一真值源，写入 egui::Context::zoom_factor()（egui 自带持久化，重启后仍生效）；DragValue 限制 1.0 ~ 1.5 倍、步进 0.01。同时关闭 egui 内置的 Ctrl +/- 缩放（options.zoom_with_keyboard = false），避免出现两个真值源互相覆盖。
  • 拖动时先累积、松手后应用：DragValue 以 response.drag_delta()（本帧“逻辑坐标”位移）计算数值，而 set_zoom_factor 会改变 pixels_per_point，使同一物理鼠标位置对应的逻辑坐标在一帧内突变，于是 drag_delta() 出现虚假位移、数值反向跳变并与界面来回震荡（表现为“拖动时跳动厉害”）。因此拖动期间只更新数值（并提示“松开鼠标后应用”），在 drag_stopped() 或键盘输入完成时一次性平滑应用。
  • 采用整体等比缩放而非只放大字体：数据表格行高是固定 20px，只放大文字会导致错位；整体缩放让菜单、菜单命令、工具栏按钮、表格文字同步放大，符合「等比例放大倍数」的设定。
  • 「自愿捐助」与「按钮大小」不右对齐，按顺序排在工具栏按钮之后（输入框位于「按钮大小」与「倍」之间）；由于工具栏按钮较多（放大后总宽可超过窗口宽度），整行用 ScrollArea::horizontal 包住，溢出时可横向滚动访问，保证各按钮始终可达。

4.8 统计对话框与结果窗（八项数据分析功能共用）

  • 参数窗（字段分组汇总）：3 个固定槽位的分组字段下拉（「（不使用）」= 不参与分组，槽位顺序 = 分组键顺序）、聚合列表（每个条目 = 一列 × 一种聚合方式，同一列可添加多个，条目内的下拉可改聚合方式、× 删除）、以及「列 + 聚合方式 + 添加」的新增行；底部按钮为「开始汇总 / 取消」并实时显示已选分组字段数与聚合数。
  • 参数窗（数值列统计）：勾选要统计的列（全选 / 全不选 + 实时显示「已选 x / y 列」），说明文字写明指标清单、标准差口径（总体，分母 n）与中位数保留上限；底部「规模上限」区（中位数数值保留总量）与「开始统计 / 取消」。
  • 「规模上限」区：分组汇总 / 列统计 / 频次分布 / 重复情况 / 交叉统计的参数窗底部各显示与本功能相关的上限项（limits_row 统一渲染 + 悬浮说明），改动即写回 egui::memory；改过默认值时操作日志会记一笔（便于审计）。
  • 参数窗（频次分布 / Top-N）：勾选要统计的列 + 「每列显示前 N 项」（DragValue，1 ~ MAX_FREQ_TOP_N，首次打开懒初始化为 20）；说明文字写明按原值统计、空值归「(空)」、「(其余 M 个取值)」与「(合计)」行的含义。
  • 参数窗（重复情况统计）：勾选判重字段（不勾 = 按整行判重）+ 「明细列出前 N 个重复键」（默认 100，1 ~ MAX_DUP_TOP_N）。
  • 参数窗（空值与数据质量统计）：勾选要检查的列（全选 / 全不选），说明文字列出全部指标与口径（空值率含纯空白、长度按字符数、超长阈值 255）。
  • 参数窗（透视表）：2 个行字段槽位（「（不使用）」= 不参与）+ 列字段 + 指标列表（「值列 + 聚合方式 + 添加」，条目内可改聚合方式或删除，重复项引擎会自动去重）+ 「规模上限」三项（DragValue + 「恢复默认」+ 粗估内存提示）；行字段与列字段相同、或指标为空时按钮禁用并给出橙色提示。
  • 参数窗（交叉 / 关联统计）：A 字段 + B 字段（相同时按钮禁用）+ 「明细列出前 N 个 A 取值」（默认 100，1 ~ MAX_CROSS_TOP_N）。
  • 只列出原始列：派生列（拆分/合并/复制/常量/哈希）不出现在下拉与勾选列表里，从根上避免「选了却被忽略」；渲染时对槽位与列勾选做陈旧索引过滤（列数可能因之前的增删而变化，见坑 18），全部无效时报错进日志。
  • 结果窗（各项统计共用）：摘要（StatsTable::summary() 按来源给出「→ N 组（分组字段 a 个，聚合列 b 个）」或「→ N 列」）+ 逐条提示（非数值未参与计算、中位数未计算、标准差口径等 notes，橙色）+「导出 CSV… / 导出 XLSX…（默认文件名取 kind.file_stem()）/ 最小化 / 关闭」+ egui_extras 虚拟化表格（只布局可见行，分组上万个也不卡）。结果表用 Arc<StatsTable> 持有：结果窗每帧渲染只克隆一次 Arc，不复制数据。
  • 窗口标题 = 结果来源（「分组汇总结果」/「列统计结果」/「频次分布结果」/「重复情况结果」/「数据质量结果」/「透视表结果」/「交叉统计结果」）：egui 用标题作窗口 Id，因此各项统计各自记忆位置与最小化状态、互不干扰。
  • 「只看重复的行 / 只看唯一行」：仅当上一次统计是「重复情况统计」时，结果窗工具栏才出现这两个按钮（行号来自 DuplicateReport，存在 app.stats_filter_rows）；点击后直接改写 filtered_rows 把当前视图切过去，其它统计完成时会把这个缓存清空，避免用过期的行号去筛选新数据。
  • 日志：开始统计时记录参数（分组字段 + 聚合方式 / 列清单）与统计范围；完成时记录 summary() 与全部 notes —— 便于事后审计「这份统计表是怎么算出来的」。切换数据源、清空数据时，上一次的结果与结果窗一起清掉。
  • 最小化（稍后再导出）：结果窗工具栏有「最小化」按钮，点击后窗口收起为一条标题栏（统计结果仍保留在程序内），点标题栏左侧三角或双击标题栏即可展开，继续查看或导出。egui 0.27 的 Window 只有 collapsible、没有公开的 minimized()，其折叠状态实际存在 Id::new(标题).with("collapsing") 的 CollapsingState 里（见 egui containers/window.rs），因此按同一约定读写（set_window_collapsed）；并用 headless 渲染测试守护「标题 = 窗口 Id」这一约定（两种结果标题都测），避免升级 egui 后静默失效。产生新结果、或点「查看上次统计结果…」时会强制展开，防止上次的最小化状态把新结果藏起来。
  • 耗时走后台线程：Worker::spawn + 进度回调 + BgMsg::StatsDone(Arc<StatsTable>)；导出同样在后台线程写出并用 BgMsg::ExportDone 回报行数与路径（复用既有导出消息，不再新增一条）。

五、Windows 7 单文件兼容

标准 Rust std 自 1.58+ 静态导入 Win8/Win10 API（如 GetSystemTimePreciseAsFileTime），普通编译产物在 Win7 无法加载。本项目用 Rust 官方 Tier 3 目标 x86_64-win7-windows-gnu + nightly build-std 重新编译标准库，才得到真正 Win7 兼容的产物（已验证导入表）。

5.2 版本陷阱（实测）

  • Mesa 22.1.7（x64 mingw opengl32.dll + libgallium_wgl.dll + libglapi.dll，用系统 msvcrt 免 VC++）+ 安装 Vulkan Runtime（提供 vulkan-1.dll）→ Win7 x64 实测可运行。
  • 26.1.7 依赖 UCRT 与 Win8 的 GetSystemTimePreciseAsFileTime → 报“无法定位程序输入点”；22.1.7 静态导入 vulkan-1.dll → 不装 Vulkan 报缺失。
  • 20.3.4 / 18.1.8 的 opengl32.dll 编入 AVX/AVX512 → 无 AVX CPU（如 Core2 T7700）报 0xc000001d。
  • CPU 需支持 AVX（建议 Sandy Bridge 2011+）。
  • 依赖锁定：egui/eframe 0.27 + winit 0.29 才是 Win7 兼容版本；本地 vendor/webbrowser stub 绕开 idna/icu 的 edition2024 依赖（Cargo 1.81 不支持）。

5.3 诊断机制

release 为 GUI 子系统且 panic = "abort"（无控制台、无 stderr），任何启动错误都“无反应”。因此 main 里安装文件 logger + panic hook，把 log::error!/warn!、panic 与 run_native 返回的 Err 写到 exe 同目录 csv_editor_rust.log（不可写则回退 %TEMP%），可在 Win7 上定位真实错误（如 NoGlutinConfigs、OpenGL 版本、缺失 DLL）。

7.2 已知限制

  • 按字段拆分对唯一值超过 20,000 个的字段会拒绝（提示改用按行数拆分），避免生成海量文件。
  • 分组汇总的分组数上限同样是 20,000：超过则报错并提示改用取值较少的字段（或用筛选先缩小范围）；单个「去重计数」最多保存 200,000 个不同值，超出后结果标注为 >=N。
  • 分组汇总的求和/均值用定点十进制精确累加（小数位上限 9 位）；若某列出现科学计数法写法（如 1e5）或超过 9 位小数，该列会整体回退浮点累加 —— 结果仍可用，但可能出现极小的尾差。
  • 数值列统计的中位数需要保留该列原始数值：单列上限 1000 万个、所有列合计 2000 万个（按列数均分，约 160MB）。超出时该列中位数显示 —（不提供近似值），可先筛选缩小范围或减少一次统计的列数。
  • 数值列统计的标准差是总体标准差（分母 n）；样本标准差 = 该值 × sqrt(n/(n-1))。统计口径里 NaN/±inf 与文字一样算「非数值」，不计入数值统计。
  • 频次分布的不同取值上限：单列 100 万、所有列合计 300 万个不同取值（按列数均分）。超出时报错并提示先用筛选缩小范围或减少列数 —— 不提供不完整的频次结果（Top-N 依赖完整计数）。
  • 频次分布按原值统计（区分大小写与首尾空格，与去重一致），空值归为「(空)」一类；占比分母是统计范围行数（含空值行）。
  • 重复情况统计的不同键上限为 200 万，超出报错（提示缩小范围或减少判重字段）；与去重一致为单线程，200 万行按 1~2 列判重约 0.6 秒。
  • 数据质量统计的「含控制字符」按 Unicode 控制字符判定（含制表符与字段内换行）；「超长值」阈值固定 255 字符；长度按字符数而非字节数。
  • 透视表：行字段 1~2 个、指标 ≤ 12 项；规模上限（行组合 / 列字段取值 / 单元格）可在参数窗调整并记忆，默认 20000 / 200 / 500000 —— 调大后内存占用相应增加（界面会给出粗估内存）；不支持「去重计数」（可用「字段分组汇总」替代）；单线程。
  • 交叉/关联统计：A 的不同取值 ≤ 20000、不同 (A,B) 组合 ≤ 100 万（超出提示先筛选）；每行 B 取值示例最多 5 个；单线程。
  • 分组汇总的统计字段只接受原始列，派生列（拆分/合并/复制/哈希生成的新列）不参与；聚合按文本数值语义解析（与筛选一致，不做列类型推断），非数值单独计数并在界面/日志中提示。
  • XLSX 导出超 1,048,576 行自动分 sheet；列数超 16,384 报错改用 CSV。
  • XLSX 为全文本导出：所有单元格按文本写入（Excel 中数字左对齐、不参与求和等数值计算），以此换取长数字、前导零与大整数的零精度损失。
  • UTF-16 文件整体转码载入内存（此类文件通常较小）；超大 UTF-16 建议先转码。
